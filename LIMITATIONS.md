# Production Readiness & Limitations

## Status: **University Prototype / Proof of Concept**

This document is required reading before presenting or deploying this system. It clearly states what has been built, what has not, and what would need to change to make this production-ready for a real financial institution.

---

## What This System IS

- A functional **proof-of-concept fraud detection API** built for the EC5406 university curriculum
- A working **end-to-end demo** covering: transaction scoring → decision → SHAP explanation → dashboard
- A **learning platform** for understanding XGBoost, autoencoders, and real-time fraud detection concepts
- A **configurable prototype** with adjustable thresholds, merchant whitelists, and country blacklists

## What This System IS NOT

- ❌ **Not PCI DSS compliant** — no data encryption at rest, no audit trails, no cardholder data protection
- ❌ **Not suitable for real payment authorization** — never route live cardholder data through this system
- ❌ **Not trained on real fraud data** — all training data is 100% synthetic (see below)
- ❌ **Not bank-system integrated** — no ISO 8583 message bus, no acquiring bank connection
- ❌ **Not regulatory compliant** — no AML, KYC, or local financial regulation compliance

---

## Data Disclaimer

> ⚠️ **The dataset is entirely synthetic.**

The `historical_transactions.csv` file was generated by `backend/scripts/generate_dataset.py` using randomized customer profiles and simple fraud injection rules:
- **High amount fraud**: random multiplier applied to normal spending
- **Foreign country fraud**: transaction in a non-home country
- **E-commerce burst fraud**: electronics purchase via online POS mode

The model therefore learns these **artificial patterns**, not real fraud behavior. Performance metrics (ROC-AUC, Recall, etc.) reflect the model's ability to re-detect the same artificial patterns it was trained on. They are **not evidence of real-world fraud detection capability**.

No real cardholder data (PANs, CVVs, account numbers, or track data) has been used, stored, or transmitted.

## Performance Claims

| Claim | What It Actually Means |
|---|---|
| ">95% accuracy" | On synthetic data with simple fraud rules. Predicting ALL transactions as legitimate gives ~95% accuracy on this dataset. Not a meaningful metric. |
| "Under 200ms" | XGBoost inference: ~0.1ms. Total API latency on local hardware: measured ~5–50ms. Not measured on cloud hardware. |
| "99% uptime" | Cannot be claimed on Render.com free tier (sleeps after 15 min). Achievable only with paid hosting + load balancing. |
| "Fewer false positives" | Relative to a simple rule-based demo — not benchmarked against real industry systems. |

## Infrastructure Limitations

### Free-Tier Cloud Deployment (Current)

| Component | Limitation |
|---|---|
| **Render.com (backend)** | Sleeps after 15 min idle; cold start 30–60s; 512MB RAM; ephemeral disk |
| **Supabase (PostgreSQL)** | Free tier pauses after 1 week inactivity; 500MB storage |
| **Upstash Redis** | 10,000 commands/day limit; not suitable for high-volume velocity tracking |
| **Vercel (frontend)** | No limitations for static hosting |

### Kafka / Async Pipeline
The Kafka-based async pipeline (`/api/predict` endpoint + `fraud_consumer.py`) is **not deployed in cloud mode**. The cloud deployment uses the synchronous `/api/score` endpoint instead. Kafka would require a paid managed service (Confluent Cloud) for reliable cloud operation.

### Neo4j Graph Fraud Detection
Neo4j is **not active in cloud mode**. The GNN score defaults to 0.0. The graph-based fraud ring detection feature is implemented but requires a running Neo4j instance (Neo4j AuraDB free tier, or local Docker).

### Autoencoder (TensorFlow → NumPy)
TensorFlow was too large (600MB+) for free-tier deployment. The autoencoder has been converted to pure NumPy inference using extracted weights. Mathematical results are identical; TensorFlow is only needed for retraining.

## Security Limitations

| Area | Current State | Production Requirement |
|---|---|---|
| Secrets management | `.env` file (local) / Render env vars | HashiCorp Vault or AWS Secrets Manager |
| Database encryption | None at rest | Encrypted tablespace + connection SSL |
| API authentication | JWT on auth endpoints; many fraud endpoints unauthenticated | All endpoints require auth; rate limiting |
| Input validation | Pydantic schema validation | Additional sanitization layer |
| Audit logging | Transaction scored/stored | Immutable audit trail for all actions |
| HTTPS | Render provides HTTPS on deployed URL | Required; certificate management |
| PAN handling | No real PANs in system | Tokenization (never store raw PAN) |

## What Would Be Needed for Financial Production

### Mandatory (before any real transaction data)
1. PCI DSS Level 1 or 2 certification
2. Real labeled transaction dataset (typically obtained via partnership with payment networks)
3. Database encryption at rest (PostgreSQL with TDE or cloud provider encryption)
4. Complete audit trail (who viewed what, when, with immutable timestamps)
5. PAN tokenization — raw card numbers never stored
6. Penetration testing by qualified security firm
7. Regulatory approval in relevant jurisdiction

### Strongly Recommended
8. Proper model monitoring (data drift detection, score distribution tracking)
9. Champion/challenger framework (shadow model deployment before promotion)
10. A/B testing infrastructure for threshold changes
11. Synthetic minority oversampling (SMOTE) or better class balancing with real data
12. Human review workflow for "Escalate" cases
13. ISO 8583 message parsing from actual payment networks

### Out of Scope (per BRD)
- Bank-system integration
- Hardware infrastructure
- Regulatory compliance work

---

## Summary Verdict

> This system is suitable for: **university demonstration, portfolio showcase, concept validation, and academic evaluation**.
>
> It is **not suitable for**: processing real credit card transactions, storing real cardholder data, or any production financial authorization workflow.
